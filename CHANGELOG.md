## 2.18.0

Bash guard: commands that Bash runs but the guard read as part of a string. Stricter on every system; a command that used to pass may now ask (research mode) or be denied (talk mode) because the guard now sees what it really runs.

- New `scripts/tuneup/bash_texto.py` (`legivel`): the command text is rewritten before it is tokenized, following the quoting as Bash does. It replaces the line-by-line heredoc removal.
- `$'...'` (ANSI-C quoting) is decoded into a plain quoted word. Before, `echo $'\'' ; rm x ; echo \'` hid the `rm` in all modes, including a write to `~/.claude/settings.json`; `$'\x72m' x` hid the command name. The same text inside `bash -c "..."` is read too (`\$` and `` \` `` inside double quotes lose the backslash, as in Bash).
- Command substitutions where the tokenizer does not split are read as commands: `"$(x)"` and backticks inside double quotes, backticks outside quotes, and `$(x)` or backticks in the body of an unquoted heredoc (`cat <<EOF`). A quoted heredoc (`<<'EOF'`) and escaped `\$(` stay text.
- Heredocs: the delimiter is read with Bash's quote removal (`<<'E-F'`, `<<"a b"`, `<<E\OF`); a `<<` inside a quoted string that spans lines is no heredoc; `<<` inside `((...))`, `${...}`, `$[...]` or `name[...]` may be a shift or a heredoc, and then both readings are checked. Before, each of these could hide the lines after it.
- Comments are dropped (a quote inside `# it's` no longer changes how the next lines are read); `\<newline>` joins the two lines without a space (`r\<newline>m x` is `rm x`) and `\\<newline>` no longer hides the next line; a line end glued to a redirection (`echo a<newline><<<x rm y`) splits the commands.
- An unclosed quote is closed at the end of the text, so the commands before it are still read one by one.
- Where the reader may not pair the quotes as Bash does (something left unclosed, a quote inside `"${...}"`, a heredoc word with an expansion, a heredoc without its end line, a `#` inside `[[ x =~ (#) ]]`) the command is also read with no quoting at all, split at every separator. Each reading is checked on its own; a `cd` of one does not reach the other.
- An unquoted `$(x)` is one word and its commands are read after the text: `rm $(x) ~/.claude/settings.json` keeps the file as `rm`'s argument (it used to pass in code mode); where a command starts, or glued to a word, it is dropped (`$(x) rm f`, `rm$(x) f`).
- A heredoc ends only at a line equal to its word (leading tabs dropped for `<<-`); before, a line with blanks around the word ended it early. When the tokenizer cannot read the text at all, the emergency split now drops quotes and splits at redirections.
- `bash -c`, `eval` and `wsl` are opened up to three levels (was one).
- Windows: `wsl [options] <command>` is read as the command the Linux shell runs (`-e/--exec`, `--cd`, `-d`, `-u`; a word with blanks is read both as one word and as shell text), and `/mnt/<letter>/...` is the drive `<letter>:` in paths and in the text check. Before, `wsl rm /mnt/c/Users/u/.claude/settings.json` passed without a question.
- New `tests/test_bash_texto.py`, with a differential test: random text is run by the real Bash with a harmless marker function, and whenever Bash runs the marker the guard must show it as a command (skipped on Windows and where there is no `bash`).
- Still open (already so before this release): substitutions are resolved in the folder where the whole command ends, and a `cd` inside `( ... )` reaches the commands after it; `eval`/`bash -c` nested more than three times, `bash -o x -c`, `bash <<E` and `| bash` are not opened; a command word that is an expansion (`$x rm f`, `"$x"rm f`); `function`, `builtin`, `coproc`; `time -p case`; `wsl ~`, `wsl -dName` and wrappers inside `powershell`/`cmd`.
- Not covered: the marketing guard (`tune-up-mkt/scripts/guarda_mkt.py`) and the panel guard (`painel/travas.py`) have their own readers and were not changed. Nothing here was run on a real Windows machine; the `wsl` reading is tested with the platform forced.

## 2.14.0

Native Windows, Part 3: the main guard (`scripts/tuneup`) reads cmd and PowerShell the way Windows users type them, tolerates a BOM in its own files, and says when Git Bash is missing. The PowerShell tool is not denied; where the guard cannot read a command it asks. Nothing changes on macOS and Linux unless stated, and every stated change is stricter.

- **`cmd`, `powershell` and `pwsh` typed in the Bash tool get the PowerShell rules** (every OS). `cmd /c|/k <x>` (also `//c` from Git Bash) and `powershell`/`pwsh -Command <x>` (also `.exe`, any path, any case) are no longer one opaque word: the guard reads the inner text and applies the same protected-path check, the same "could not read this PowerShell command" question (`-EncodedCommand`, an open quote, a here-string, `--%`) and the same talk and research rules as the PowerShell tool, so the same text gets the same verdict in both tools. `--x` and `/x` spellings of the executable's own switches (`--enc`, `/wd`) are read as `-x`, and an unknown one asks. `-WorkingDirectory`/`-wd` is followed. A `cd` inside the wrapper applies to the wrapper's own commands only, as in a real shell; when the command has `$'` (which the splitter does not understand) the `cd` still carries on to the commands after it.
- cmd text is rewritten before the check (new `scripts/tuneup/powershell_cmd.py`): `del`, `erase`, `rd`, `rmdir`, `move`, `copy`, `xcopy`, `robocopy`, `replace`, `ren`/`rename` become `rm`/`mv`/`cp` (switches like `/s /q` and glued `rd/s/q` dropped, `%VAR%` read as `$VAR`, `%HOMEDRIVE%%HOMEPATH%` as `~`, `^` escapes and `N>&M` dropped, `\` read as `/`), also after `@`, `call`, `start [/b]`, a nested `cmd /c` or `%COMSPEC% /c`, `if [not] exist X`, `if errorlevel N`, `if a == b`, `else` and `... do`; `cd|chdir [/d] X`, glued `cd\x` and `pushd X` are followed. A piece that cannot be tokenised, an `if` the guard cannot read with a verb in it, a verb left unread (outside `echo`/`rem`) and a verb on a loop variable (`for %d in (...) do rd %d`) ask. There is no variable resolution, so `set x=...` followed by `%x%`, and any delayed `!x!`, ask. `%VAR%` is read in any case (`%UserProfile%`), and `cmd /r`, glued switches (`/q/c`, `/v:on /c`) and text glued to the switch (`/cdel x`, `/c"del x"`) are read; text after `cmd` with no readable `/c|/k|/r` asks.
- A link is a write: cmd's `mklink [/D|/H|/J] link target` and PowerShell's `New-Item -ItemType Junction|SymbolicLink|HardLink` are read as `ln -s target link`, so linking a protected folder (`mklink /J .tune-up ~/A/.tune-up`) asks, the same as `ln -s` already did. `-Type` (alias of `-ItemType`) is read too.
- Home: `~\` expands like `~/` on Windows, and PowerShell's `$env:HOMEDRIVE$env:HOMEPATH` (also `${env:...}`) reads as `~`. `$env:HOMEDRIVE` alone no longer matches as `$env:HOME`.
- PowerShell common parameters (`-ErrorAction`/`-ea`, `-WarningAction`, `-InformationAction`/`-infa`, `-ProgressAction`/`-proga`, `-ErrorVariable`, `-OutVariable`, `-OutBuffer`, `-PipelineVariable` and their aliases) take a value that is not a path: `Copy-Item x ~\.claude\settings.json -ErrorAction Stop` no longer hides the target.
- Pipelines: a write or copy cmdlet fed by a pipe and without a path of its own (`gci <protected> -Recurse | Remove-Item`, `gci evil -Filter settings.json | Copy-Item -Destination ~/.claude`) checks the paths read before it; when the feeder lists a folder the targets include `<folder>/<-Filter or *>`. A cmdlet that uses `$_`/`$PSItem`, and any other consumer that is not read-only (`% { $_.Delete() }`, `% Delete`), gets those paths too. More than 50 fed paths for one consumer, or more than 300 statements, asks: the hook has 15 s and a long pipe must not buy a timeout.
- Redirections to an unquoted `$null`, `NUL`, `NUL:` or `/dev/null` in PowerShell text are no write, so talk and research modes stop blocking `git status 2>$null` in the PowerShell tool and inside `pwsh -c`; quoted (`'$null'`, `"nul"`) it is a file. In plain Bash only `/dev/null` (and `NUL` on Windows) is null: `$null` stays a write there, because Bash can bind that name. `Select-Object`, `Where-Object`, `Sort-Object`, `Measure-Object`, `Out-Null`, `Format-*` and their aliases are read-only, matched on the bare name only (`sort.exe`, a path or a module-qualified name is not) and not when they carry `-OutFile`/`-Destination`/`-OutVariable`/`-ov` or, for `sort`, an output switch (`/o`, `-o`, `--output`). A `Where-Object`/`?` block that is a plain comparison (`$_.Length -gt 1`) is read-only; one with a parenthesis, the call operator `&` or dot-sourcing is not.
- **A PowerShell write whose target the guard cannot read asks** (new `scripts/tuneup/powershell_alvo.py`): a write, copy, remove, `New-Item` or `Expand-Archive` whose path is a variable (`$d/settings.json`, `$f.FullName`; `$HOME`, `$env:X` and the pipe's `$_` are still read), contains `$(` or a .NET call (`::`), or is a subexpression `(...)` outside a value parameter. A method called on a subexpression (`(dir X).Delete()`, `.MoveTo()`) and a `%`/`ForEach-Object` consumer that is not read-only (`% Delete`, `% { $_.Delete() }`) are read as removing the paths fed to them; `% Name`, `% FullName` and `% { $_.Prop }` stay read-only. New reason `ps_alvo_variavel` (en, pt-BR). Stricter on every OS: `Remove-Item $x`, `$PWD` or `$PSScriptRoot` targets and `New-Item (Join-Path $a b)` now ask.
- A command with a NUL byte asks, in both tools (every OS).
- User-editable files written by PowerShell 5.1 (UTF-8 with BOM) are read with `utf-8-sig`: `usuario.py`, `config.py` (project config and trust file; the trust sha256 is still taken on the raw bytes), `escrita.py` (a BOM used to empty `protected_paths` in silence), `agent.py`. `titulo_terminal.py` keeps the BOM and the line endings it found when it rewrites a file, and inserts lines in the file's own line ending; **on macOS/Linux a CRLF settings file is no longer rewritten as LF.**
- Small ones: `git add ./*`, `.*`, `.\*` and `.\` count as broad adds (**every OS**; `./*` was not caught before); `open(r"...", "w")` with a string prefix (`r`, `b`, `f`, `u`, `rb`, `br`, `fr`, `rf`) is a write; `wsl` and `setx` naming tune-up get the profile level on Windows only (the inner command of `wsl` is not opened); `sessao.py` retries `os.replace` up to 5 times, 30 ms apart, on `PermissionError`; `info.py` gives paths with forward slashes on Windows (skills paste them into Bash).
- Git Bash is required on Windows. Without it Claude Code runs hooks in PowerShell, `sh` is missing there, the error does not block, and every guard is silently off. The panel now says so at the top of the screen and on its stderr (`painel/aviso_sh.py`, a copy of `scripts/tuneup/gitbash.py`; a test fails if the two drift). Git Bash is looked for in `CLAUDE_CODE_GIT_BASH_PATH`, on PATH outside System32 and WindowsApps, next to an absolute `git.exe`, and under `ProgramFiles`, `ProgramW6432`, `ProgramFiles(x86)` and `LocalAppData\Programs`. SessionStart has the same line, which only shows the day hooks run without `sh`; README, panel README and the setup skill say Git Bash is required. `hooks/hooks.json` was not changed: Claude Code picks the hook shell per hook (`bash` or `powershell`), not per system, so a PowerShell twin of `scripts/py` cannot be wired without breaking macOS/Linux.
- Tests: `tests/test_win3_shell.py`, `test_win3_escrita.py`, `test_win3_bom.py`, `test_win3_sh.py`, `painel/test_win3_sh.py`, and one new case in `tests/test_seg_caminhos.py` (links); the last review round added four tests (`test_r3_*`). No older test changed its expectation.
- Not proven here (no Windows machine, Windows CI never ran): real `cmd.exe`/PowerShell 5.1 and 7 parsing of the cases above (switch spellings, glued `cd`, `start` titles), MSYS argument conversion of `//c`, `NUL` under Git Bash, a real junction, a BOM file written by PowerShell 5.1, the `PermissionError` retry against a real open handle, and the panel warning on a machine without Git for Windows.
